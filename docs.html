A unified, microservices-based AI Infrastructure Platform designed to handle high-concurrency LLM workflows, real-time streaming RAG, and distributed agent orchestration.

Platform Architecture

1. AI Gateway

A high-performance HTTP reverse proxy written in Go. Intercepts LLM requests to optimize cost and latency.

  • Semantic Caching: Uses Redis to cache exact or semantically similar prompts, reducing latency from 500ms to <5ms.
  • Shadow Routing: Asynchronously duplicates production traffic to experimental models for offline evaluation without impacting user latency.

2. Streaming RAG Engine

A Go and PostgreSQL (`pgvector`) service designed for mutating, real-time data environments.

  • WebSocket Ingestion: Accepts continuous data streams.
  • Transaction Batching: Uses Go channels and background workers to batch upserts, preventing database connection saturation under high load.
  • HNSW Indexing: Queries run directly in Postgres using approximate nearest neighbor search.

3. Agent Orchestrator

A distributed execution engine utilizing NATS message queues to decouple reasoning from execution.

  • Go Router: Decomposes complex user goals into atomic sub-tasks.
  • NATS Broker: Provides lightweight, high-throughput message routing with Request-Reply patterns.
  • Python Workers: Stateless nodes that listen to Queue Groups, automatically load-balancing tasks across the cluster.

System Design & Trade-offs

Designing this platform required several critical architectural decisions focused on scalability, consistency, and latency.

Why NATS instead of Kafka for Agent Orchestration?

Kafka is excellent for persistent, high-throughput event streaming, but it introduces significant operational overhead and latency. For AI agent orchestration, tasks are typically ephemeral and require synchronous Request-Reply patterns (the Go router needs the Python worker's result immediately). NATS is extremely lightweight, inherently supports Request-Reply over queues, and has sub-millisecond latency, making it the superior choice for intra-agent communication.

Why Batching in WebSockets?

A naive WebSocket implementation writes to the database immediately upon receiving a frame. At 10,000 messages/sec, this creates 10,000 discrete transactions, overwhelming PostgreSQL's connection pool. By buffering events in a Go channel and flushing them via a single bulk transaction every 500ms (or when the buffer hits 100), we achieve massive throughput while maintaining ACID guarantees.

Local Development Guide

1. Start the Infrastructure

Spin up Redis, PostgreSQL (pgvector), and NATS locally.

docker compose up -d

2. Run the Gateway

Start the API Gateway to test semantic caching.

cd gateway
go run main.go

Test with cURL (run twice to see cache hit):

curl -X POST http://localhost:8080/v1/completions \
  -H "Content-Type: application/json" \
  -d '{"prompt": "How do I reset my password?", "model": "gemini-pro"}'

3. Run the Streaming RAG

Start the ingestion engine and query it.

cd streaming-rag
go run main.go

4. Run the Orchestrator

Start the Python worker and Go router in separate terminals.

# Terminal A: Start Python Worker
cd orchestrator/worker
source venv/bin/activate
python worker.py

# Terminal B: Start Go Router
cd orchestrator/router
go run main.go
